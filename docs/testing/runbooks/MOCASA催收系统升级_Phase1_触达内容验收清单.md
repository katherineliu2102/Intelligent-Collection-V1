## 1. 本文的职责

系统侧断言只能证明**"系统认为发出去了"**：timeline 有 `DELIVERED`、有 `provider_msg_id`、步骤转终态。
以下几类问题在系统侧一律显示正常，只能靠内容层面的验收发现：

- 终端上实际渲染的正文错误：金额格式、姓名、逾期天数、语言、币种
- 该发的漏发，或不该发的多发（尤其"应为 0 封"的场景）
- 正文含不该出现的 PII、内部标识或调试字段
- Push 标题/正文被截断，SMS 被拆分成多条

`t_contact_timeline` 在 Phase 1 刻意不保存正文与变量值，只留 `content_summary`、`script_slot`、
`template_version` 与 `content_hmac`（`content_key_id` 仅标识密钥版本，不保存密钥）。这是合规设计，
代价就是**内容正确性必须由本文承载**。

**边界**：本文不定义用例、不定义环境、不作阶段放行裁决。文案本身的 SSOT 在
[渠道模板清单与配置 §2 全渠道 scriptSlot 总表](../../channel/MOCASA催收系统升级_Phase1_渠道模板清单与配置.md#2-全渠道-scriptslot-总表)；
本文只维护"某场景的某一步应该出现哪个 slot、以及人工如何确认"。

## 2. 两种核对模式

| | 模式 A · 自持终端（T3 / L4b） | 模式 B · 间接取证（T4 Pilot） |
|---|---|---|
| 终端归属 | 测试手机、测试邮箱、测试 Push token 在自己手上 | 真实客户设备，**不可查看** |
| 核对方式 | 直接肉眼比对全文与 §3 期望 | 受控 preview 渲染 + 供应商投递回执 + timeline 审计字段三方比对 |
| 文案来源 | Phase 1 占位话术 | 正式话术，**必须业务预先批准并冻结** |
| 抽检比例 | 全量 | 按批准比例抽检，异常场景 100% |
| 失败处置 | 修配置后重跑 | 零容忍阻断，立即冻结当批 |

模式 B 不得以"客户没投诉"作为内容正确的证据。

## 3. 期望触达矩阵

> 文案列填 scriptSlot，不硬编码渲染结果——渲染值随案件数据变化，写死会立刻过期。
> T4 Pilot 的批准文案在业务冻结后由编排同事填入"批准文案编号"列。

### 3.1 按 stage 的计划步骤期望

| 场景 | stage | 步骤序 | 渠道 | 期望 scriptSlot | 批准文案编号（T4 填） |
|---|---|---|---|---|---|
| 当日到期 | S0 | 1 | SMS | `S0_DUE_TODAY` | — |
| 早期逾期 | S1 | 1 | SMS | `S1_SMS_STANDARD` | — |
| 早期逾期 | S1 | 2 | Push | `S1_PUSH_STANDARD` | — |
| 中期逾期 | S2 | 1 | SMS | `S2_SMS_STANDARD` | — |
| 中期逾期 | S2 | 2 | Push | `S2_PUSH_STANDARD` | — |
| 中期逾期 | S2 | 3 | SMS | `S2_SMS_STANDARD` | — |
| 后期逾期 | S3 | 1 | SMS | `S3_SMS_STANDARD` | — |
| 后期逾期 | S3 | 2 | Push | `S3_PUSH_STANDARD` | — |
| 末期 | S4 | 1 | SMS | `S4_SMS_STANDARD` | — |
| 末期 | S4 | 2 | Email | 见 §3.3 里程碑判定 | — |

步骤序与渠道组合以计划模板为准；若模板变更，本表须同步更新后才可用于验收。

### 3.2 渲染要点

不逐案抄正文，只固定必须核对的渲染点：

| 渲染点 | 期望 |
|---|---|
| 金额 | `%,.2f` 千分位两位小数，带 `PHP` 或 `₱` 前缀，与案件应还金额一致 |
| 姓名 | 与案件投影一致，无占位符残留 |
| 逾期天数 | 与执行时 dpd 一致；S0 场景不出现"overdue" |
| 语言 | 英文；无中文残留、无未替换变量 |
| 品牌前缀 | SMS 以 `MOCASA` / `MOCASA Collections` 开头 |
| 长度 | SMS 单条不拆分；Push 标题在真机不截断 |

### 3.3 Email 里程碑

Phase 1 的 Email **仅在精确 DPD 里程碑日**发出，Resolver 对非里程碑返回 null，步骤记 `SKIPPED` 且不调用供应商。

| scriptSlot | 触发 dpd |
|---|---|
| `S0_DUE_TODAY_EMAIL` | 0 |
| `S1_EMAIL_OVERDUE_NOTICE` | 1 |
| `S2_EMAIL_ENTRY` | 4 |
| `S4_EMAIL_ENTRY` | 31 |
| `S4_EMAIL_PRE_CLOSE` | 75 |

发件人 `collections@mocasa.com`；Subject 在 SendGrid 控制台配置，SSOT 见
[`email-templates/subjects.md`](../../email-templates/subjects.md)。

测试案件的 dpd 通常不落在里程碑上，因此**收到 0 封邮件是预期结果，不是故障**。
需单独验证 Email 渲染时走 L4a Email E2E，见
[渠道功能测试指南](../../channel/MOCASA催收系统升级_Phase1_collection-channel功能测试指南.md) 的 `TC-EMAIL-*` 用例。

## 4. 不该发的清单

"应为 0"的断言最容易被漏检——没收到消息时，人会默认一切正常。每轮必须逐条确认。

| 场景 | 期望 | 若违反 |
|---|---|---|
| Email 里程碑未命中 | 0 封邮件，步骤记 `SKIPPED` | 内容阻断，排查 Resolver |
| 案件已全额结清 | 结清后不再有任何触达 | **零容忍**，立即冻结 |
| 案件已停催（D91+） | 停催后不再有任何触达 | **零容忍**，立即冻结 |
| 升档取消的旧计划 | 旧计划剩余步骤不再触达 | 内容阻断，排查取消时序 |
| 触达窗口外 | 窗口外无任何触达 | **零容忍**，合规问题 |
| 非白名单案件（T3/T4） | 名单外一律零触达 | **零容忍**，立即冻结 |
| 重复投递或重放 | 同一步骤不产生第二条 | 内容阻断，排查幂等 |

## 5. 模式 A 核对流程（T3 / L4b）

前置：环境、造数、发布与查库节奏见 [L4b 环境交接清单](./MOCASA催收系统升级_Phase1_L4b环境交接清单.md)。
测试地址（手机、邮箱、Push token）不写入本文，从该 Runbook 的环境配置取。

1. 记录本轮的执行时间窗，作为筛选终端消息的依据。
2. 按 §3.1 统计本轮各渠道**应收条数**，先算期望再看终端，避免先入为主。
3. 逐条比对终端实收内容与 §3.2 渲染要点。
4. 逐条走 §4 不该发的清单。
5. 用受控 preview 接口渲染同一案件的正文，与真机收到内容比对（接口见 L4b 环境交接清单）。
6. 与系统侧 `DELIVERED` / `SKIPPED` 结果交叉核对，差异必须有解释。

### 核对 Checklist

- [ ] 各渠道实收条数 = §3.1 推算的期望条数
- [ ] 每条正文的 slot 与 §3.1 一致
- [ ] §3.2 六个渲染点全部正确
- [ ] Email 实收数与 §3.3 里程碑判定一致
- [ ] §4 七条"不该发"全部为零
- [ ] preview 渲染结果与真机一致
- [ ] 系统侧 `DELIVERED` / `SKIPPED` 与终端观测一致
- [ ] 无 PII 出现在日志、SQL 输出或截图中

## 6. 模式 B 核对流程（T4 Pilot）

真实客户设备不可查看，改为三方比对：

| 证据源 | 提供什么 | 局限 |
|---|---|---|
| 受控 preview 渲染 | 该案该步的完整正文 | 证明"会渲染成什么"，不证明"已送达" |
| 供应商侧回执 | 投递状态、目标地址、时间 | 证明"已送达",不证明内容 |
| `t_contact_timeline` | `script_slot`、`content_summary`、`content_hmac`、`provider_msg_id` | 证明"系统发的是哪个 slot" |

三者必须互相咬合：preview 的 slot = timeline 的 `script_slot`，timeline 的 `provider_msg_id` 能在供应商侧查到，
且投递地址属于批准白名单。任一环断裂即视为无法验收。

**Pilot 前置**：正式文案须经业务批准并冻结，批准编号填入 §3.1；未冻结文案不得对真实客户发送。
`CONTENT_AUDIT_HMAC_KEY` 与 `CONTENT_AUDIT_KEY_ID` 须通过 Secret 注入，未注入时 `content_hmac` 为 null，
该轮不得将其作为内容完整性证据。

## 7. 内容红线

任一发生即为阻断项，须冻结并按测试 SSOT 的回滚原则处置：

1. 正文含真实 PII 泄露给非本人，或含内部案件标识、调试字段
2. 金额或姓名错误
3. 对已结清或已停催案件发出催收内容
4. 触达窗口外或超出合规频次
5. 向非批准白名单地址发送
6. 日志、SQL 输出、截图或本文档中出现未脱敏的手机号、邮箱、token

## 8. 备注

- Phase 1 话术为占位版本，正式版由编排同事提供；本文只引用 slot，不承担文案定稿。
- `template_version` 记录应用侧模板版本，与管理后台发布版本无稳定映射，不能仅凭该字段回放原文。
- 单次运行的实际观测结果写入带日期的测试报告，不回写本文。
