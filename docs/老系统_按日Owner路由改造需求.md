## 1. 目标与边界

**目标**：任一 `caseId` 在任一 PHT 自然日只有一个执行 owner；owner 以日为粒度在两系统间切换。

**边界**：

- 不改动老系统与贷款核心的既有入案链路；不改动老系统对外出参格式。抑制与重建逻辑在老系统内部消化。
- 数仓是路由决策唯一权威；老系统不得按本地规则重算或覆盖 owner。
- 已提交给渠道供应商的在途请求不可撤回（与新系统口径一致）；双方共同保证的是**不再产生新的触达**。

## 2. 接口：每日 Owner 抑制清单

### 2.1 投递方式

| 项 | 约定 |
| --- | --- |
| 载体 | 新 Pub/Sub topic（建议命名 `collection-owner-routing-v1`；数仓发布、老系统订阅） |
| 发布方 | 数仓（owner 决策与其每日案件批次同源，天然一致） |
| 时间 | 每日 **03:30 PHT 前**发完（数仓 owner 批次约 03:00 完成后立即派生） |
| 消息形态 | 逐案消息，envelope `{dataType, data}`，`data` 单案 payload |
| 可靠性 | 重投 / 重放复用原 `eventId`，老系统幂等吸收；Topic 开保留与 DLQ，按既有 topic 惯例配置 |

### 2.2 消息字段

逐案消息（当日该案 owner 为 NEW）：

```json
{
  "dataType": "ownerRoutingEvent",
  "data": {
    "eventId": "6f0c8b1e-5c2a-4d3e-9f1a-2b7c8d9e0f1a",
    "caseId": 483877,
    "userId": 3780028,
    "owner": "NEW",
    "routingDate": "2026-09-03",
    "batchSeq": 1
  }
}
```

| 字段 | 必填 | 口径 |
| --- | --- | --- |
| `eventId` | 是 | publish 前 UUID；重试 / 重投 / 重放复用 |
| `caseId` | 是 | `loan_id`，与案件消息口径一致 |
| `userId` | 是 | 用户标识（同用户多案同日同 owner，由数仓分桶保证） |
| `owner` | 是 | 固定 `NEW`（清单只列 NEW 案件；不在清单 = LEGACY） |
| `routingDate` | 是 | 清单归属日，`yyyy-MM-dd`，PHT 日历日 |
| `batchSeq` | 是 | 当日批次序号，正常每日一批 = `1`；应急同日重发递增（见 2.3） |

**空批次 marker**：当日 NEW 案件数为 0 时（整体回滚、维护窗口），数仓必须发布一条：

```json
{
  "dataType": "ownerRoutingEvent",
  "data": { "eventId": "…", "routingDate": "2026-09-03", "batchEmpty": true, "batchSeq": 1 }
}
```

> 为什么必须有 marker：老系统无法区分「今日清单确实为空」与「发布失败」。没有 marker，回滚日（全 LEGACY）老系统会永久维持前一日抑制，最后一批 NEW 案件无人催收。

### 2.3 同日应急重发（Day-1 回滚通道）

新系统当日故障且不可修复时，数仓以 `batchSeq` 递增**重发当日完整清单**（如回滚则重发空批次 marker，`batchSeq=2`）。老系统规则：

- 以当日收到的**最大 `batchSeq` 的完整批次**为准，原子替换当日抑制集合；
- 低 `batchSeq` 批次的迟到消息按 `eventId` 幂等丢弃；
- 同日重发属于人工应急动作，须双告警（数仓 + 老系统各记审计）。

## 3. 改造动作（五项）

| # | 动作 | 行为约束 | 异常边界 |
| --- | --- | --- | --- |
| 1 | **日抑制** | 收到当日有效清单（含 marker）后，对清单内案件：停住当日及后续未执行 plan 步骤（不 dispatch）；案件标记「当日归新系统」（建议保留计划数据仅作冻结，便于审计与恢复） | 在途请求不撤回 |
| 2 | **零收保护** | 03:30 PHT 前未收到任何当日清单消息（含 marker）→ **维持昨日抑制 + 告警**，不得自行解除；人工按 Runbook 处置 | 与新系统「当日零收不对账」规则互为镜像，防双触达 |
| 3 | **重入重建** | 案件不在当日有效清单 → 恢复执行：以当前 DPD 重新对齐计划节奏，**跳过已过期日块、不追溯补发**；重入首日触达不早于重入日。实现方式（挂起计划修剪 / 整体重建）由老系统自定 | 行为验收见 §5 |
| 4 | **在途请求** | 已发出的渠道请求接受其自然完成；只保证此后不再产生新触达 | 与新系统口径一致 |
| 5 | **事实回流** | 触达 / 回款 / 成本事实按日回流数仓（已有则确认口径对齐）；可提供当日触达摘要 | 跨系统效果比较与 Phase 2 频控的数据基础 |

## 4. 时序约束

```text
03:00 PHT  数仓 owner 决策批次完成（caseEvent 只发 NEW）
03:30 PHT  抑制清单到老系统 → 老系统停手（冻结清单内案件）
03:35 PHT  新系统缺席对账 → 迁出 / 重入接管
08:00 PHT  当日首槽触达开始（交接已在首槽前完成，无同窗竞争）
```

老系统「收到即停」，天然满足 08:00 前完成交接；无需与新系统对时。

## 5. 验收标准

| # | 场景 | 通过标准 |
| --- | --- | --- |
| 1 | 常态轮换 | 任意 `caseId` 在同一 PHT 自然日于两系统触达事实同时存在 → **必须为 0**（数仓按日对账两侧触达事实） |
| 2 | 重入 | 老系统重入首日的触达不早于重入日；无历史日补发 |
| 3 | 零收保护演练 | 模拟清单缺失（断开发布）→ 老系统维持昨日抑制、告警触发、无双触达 |
| 4 | 回滚正确性 | 空批次 marker 日 → 老系统恢复全部案件执行；`batchSeq` 重发日 → 按最新批次接管 |
| 5 | userId 一致性 | 同 `userId` 多案同日只有一个执行 owner（数仓分桶 + 两侧共同遵守） |

## 6. Phase 1 已知限制

- **跨系统周频控不合并**：轮换边界上两系统的周累计触达可能叠加，Phase 1 接受为已知限制；数仓监控投诉 / 退订指标，Phase 2 基于触达事实回流补齐。日内频控天然安全（同用户同日单 owner）。
- **新系统对账失败日**：NEW cohort 当日零触达（新系统门控关闭 + 老系统维持抑制）；恢复路径见[开发计划 §5](./testing/MOCASA催收系统升级_Phase1_按日Owner路由开发计划.md#5-待拍板项)。

## 7. 开放问题

1. 老系统内部「冻结计划」的具体实现（冻结标记 / 取消重建 / 跳过）由老系统团队定；本需求只约束 §3 / §5 的外部行为。
2. 清单消息是否需要携带产品、DPD 等附加字段（当前最小集 `caseId` / `userId` / `routingDate`）——老系统评审时确认。
3. 老系统事实回流若已有既有通道，需与数仓对齐「按归属日 + 案件粒度」的口径（对比分析依赖），不复用则另议。
