# 讨论材料：数仓驱动的并行催收路由
> **状态**：讨论稿，未纳入 Pub/Sub 契约或代码实现  
> **目标**：在新旧催收系统并行的 1–2 个月内，由数仓按比例调配案件，同时避免两个系统对同一案件执行后续触达。

## 1. 背景与结论

新系统上线初期需要小流量验证，并允许按日调整进入新系统的案件比例；后续全量切入新系统。建议数仓在每日完整 `caseEvent` 中下发 `collectionOwner`，作为当日案件唯一触达归属：

```text
NEW     新催收系统可建计划、可执行触达
LEGACY  旧催收系统可处理；新系统只保留投影，不建或执行计划
```

数仓仍只计算、发布消息，不直连、不写 `t_ai_collection`；`collection-ingestion` 仍是该表唯一写入者。该方案不新增 Pub/Sub Topic 或内部事件类型。

## 2. 旧方案（删除 `t_ai_collection` 行）及其弊端

曾考虑的旧方案：新系统完成一轮催收后，随机标记部分案件“扔回旧系统”，并在新系统中**删除**对应 `t_ai_collection` 行，期望次日 `caseEvent` 不再触发新系统催收。

该方案不建议采用，主要问题如下：

| 问题 | 说明 |
| --- | --- |
| 不能表达有效移交状态 | 数仓仍每日下发完整 `caseEvent`；删行后，补发或重放会再次 upsert。Redis `ingested:{caseId}` 尚在时只刷新投影、丢失时可能再次建计划；“行不存在”无法稳定表达案件已交旧系统。 |
| 存量计划停止不确定且原因失真 | 已有计划不会因删投影行立即停止；下一次步骤执行时 `PreFlightChecker` 才读不到案件并以 `CASE_NOT_FOUND` 取消，无法区分数据异常与有意移交。 |
| 审计和对账证据缺失 | 删除投影会丢失 DPD、金额、inbox 对应关系及移交时点，无法追溯案件何时由谁负责，也无法可靠解释发布、接入和计划状态的差异。 |
| 调配时机不适合回退保护 | 在新系统跑完一轮流程后才随机回流，不能保护正在发生故障的在催案件；每日重新随机也不利于短期并行中的稳定切量和回滚。 |

结论：交接应通过**持久、可审计的 `collectionOwner` 字段**表达，并配合 PreFlight 阻断后续触达；**不应**以删除 `t_ai_collection` 行作为移交手段。

## 3. 每日流程

```text
数仓按当日目标比例分配每个在催 case 的 collectionOwner
  ↓
每日完整 caseEvent 携带 collectionOwner
  ↓
新系统接入层更新 t_ai_collection.collection_owner
  ↓
前一 owner = LEGACY，当前 owner = NEW
  → 复用已有 CASE_INGESTED，按当日 DPD / stage 建新计划

前一 owner = NEW，当前 owner = LEGACY
  → 不新增内部事件；后续步骤在 PreFlight 读到 LEGACY 后取消计划并拒绝渠道调用

owner 未变
  → 仅刷新投影，沿用现有每日快照语义
```

旧系统必须从同一数仓归属结果中仅选择 `collectionOwner=LEGACY` 的案件；新系统仅允许 `collectionOwner=NEW` 的案件触达。双方以同一字段作为唯一触达开关。

## 4. owner 变化时的行为

| 变化 | 新系统行为 | 旧系统行为 |
| --- | --- | --- |
| 首次 `NEW` | 创建计划 | 排除该案 |
| `LEGACY → NEW` | 复用 `CASE_INGESTED` 建计划 | 停止后续催收 |
| `NEW → LEGACY` | PreFlight 阻断后续步骤，计划以 `OWNER_CHANGED` 取消 | 在约定生效时间后接管 |
| `NEW → NEW` | 刷新投影，不重复建计划 | 持续排除 |
| `LEGACY → LEGACY` | 刷新投影，不建计划 | 持续催收 |

`NEW → LEGACY` 不删除 `t_ai_collection` 行。投影保留数仓事实、owner 变更和消息审计，便于对账、排障与重放；删除行无法证明案件已移交，且会破坏投影单写者和重放语义。

已提交给外部供应商的 AI_CALL 无法可靠撤回；本方案保证 owner 变化后的**后续**步骤不再由新系统发起，不能撤销已发生的外部动作。

## 5. 生效时间与双催防线

建议数仓增加 `ownerEffectiveDate`（`yyyy-MM-dd`，Asia/Manila），使归属变更按自然日生效：

1. 数仓在日切前发布带新 owner 的完整快照。
2. 新系统接入并更新投影；owner 不为 `NEW` 的后续步骤被 PreFlight 拦截。
3. 旧系统仅在 `ownerEffectiveDate` 到达后处理 `LEGACY` 案件。

这使调配可以每天发生，而不是在同一个触达窗口内两边抢占案件。具体日切时间、旧系统任务开始时间与消息消费完成门控需由数仓、旧系统和运维共同确认。

## 6. 数仓需确认的契约项

| 项目 | 建议 | 需数仓确认 |
| --- | --- | --- |
| 新字段 | 每条 `caseEvent.data` 必带 `collectionOwner`，值为 `NEW` / `LEGACY` | 是否可在每日完整快照产出 |
| 生效时间 | 建议必带 `ownerEffectiveDate` | 是否可按 PHT 自然日生成 |
| 分配算法 | 由数仓按当日目标比例随机/分层随机分配 | 分层维度、随机种子、审计口径 |
| 快照指纹 | `collectionOwner`、`ownerEffectiveDate` 必须纳入 `caseVersion` 输入 | 否则仅 owner 改变时指纹不变，接入会按现有幂等规则跳过更新 |
| 历史查询 | 旧系统须获取当日 owner 结果 | 旧系统读数仓视图、文件或消费同一事实流，具体方式待确认 |
| 还款增量 | `repaymentEvent` 是否携带 owner 待确认；默认沿用当前投影 owner | 保证 owner 切换与还款并发时的处理口径 |

`collectionOwner` 不是数仓写业务库的权限；它只是数仓发布的案件事实字段，业务投影仍由接入层写入。

## 7. 新系统实现范围（待确认后）

- `t_ai_collection`、`CaseProjection`、`CaseInfo` 增加 `collectionOwner` 与 `ownerEffectiveDate`。
- `caseEvent` mapper、投影写入 SQL 和 `CaseService` 映射新字段。
- 接入层以投影中前后 owner 判断是否复用 `CASE_INGESTED`；不再以 Redis `ingested:{caseId}` 作为 owner 切换后建计划的唯一判断。
- `PreFlightChecker` 在现有实时查询中校验 `collectionOwner=NEW`，无需额外查询；不满足时取消计划，原因新增 `OWNER_CHANGED`。
- 日切仅扫描 `collectionOwner=NEW` 的投影。
- 清理未投入 Phase 1 的取消原因：`COMPLAINT`、`MANUAL`、`PTP_EXPIRED`；`MANUAL_CLEANUP` 是否保留为迁移兼容值另行确认。

以上不新增 Pub/Sub Topic、内部 EventType 或租约状态机；`CASE_INGESTED` 继续用于 `LEGACY → NEW` 的建计划。

## 8. 对齐验收与待决策问题

上线前至少验证：

1. `NEW → LEGACY` 后，新系统不再发起新的渠道调用，旧系统在生效日后接管。
2. `LEGACY → NEW` 后，新系统仅创建一个与当日 stage 匹配的计划。
3. 仅 owner 改变时，`caseVersion` 改变且投影更新。
4. 每日对账满足：所有在催 case 恰好属于 `NEW` 或 `LEGACY`；两系统实际触达范围无交集。
5. Pub/Sub 重放不改变同一份 `collectionOwner` / `ownerEffectiveDate` 的处理结果。

待数仓、旧系统和运维确认：

- 每日目标比例是全量随机、按 DPD / 产品分层随机，还是指定名单；
- owner 变更是否允许当天生效，还是统一次日生效；
- 旧系统读取 owner 的技术路径及其最早可接管时间；
- `repaymentEvent` 在 owner 切换窗口内的优先级与字段口径；
- 出现新系统故障时，是将全部 owner 改为 `LEGACY`，还是仅调整后续入案比例。
