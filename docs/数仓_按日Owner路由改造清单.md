## 1. 改造清单

| # | 改造项 | 说明 | 是否闸灰度 |
| --- | --- | --- | --- |
| 1 | `caseEvent` 增加 `owner` 字段 | 必填、发给新系统的案件固定 `NEW`（契约 §2.2 字段表） | ✅ |
| 2 | **发布范围改造** | 现状为 `dpd >= -3` 全量逐案发布；改为**仅发当日 `owner=NEW` 案件**（契约 §1.1 / §2.2 / §3.5）。LEGACY 案件不发消息——新系统按「缺席即迁出」对账，这是整个轮换机制的成立前提 | ✅（核心） |
| 3 | owner 决策逻辑 | userId 稳定分桶后逐案输出 owner；**分流比例必须做成可配置**（后续持续扩量、每日进案量不固定，不能硬编码） | ✅ |
| 4 | `occurredAt` 语义 | 每日 `caseEvent.occurredAt` 的 PHT 日历日 = 当日归属日（已确认，落进发布任务约束） | ✅ |
| 5 | 迟到 / 补发规则 | 复用原 `eventId` / `caseVersion` / `occurredAt`；**批后不得翻案**（已判 LEGACY 的案件改判 NEW 次日批次生效；当日迟到补发可当日到达） | ✅ |
| 6 | `repaymentEvent` 保持全量 | **明确不过滤**：LEGACY 案件的还款事件到达新系统仅刷新投影、无活跃计划可取消，无害且保持投影新鲜（契约只对 `caseEvent` 收紧了范围） | — |
| 7 | **每日 Owner 清单发布**（新 topic） | 新 topic `collection-owner-routing-v1`，逐案 `ownerRoutingEvent`（`caseId` / `userId` / `routingDate` / `batchSeq`）+ **空批次 marker**（当日零 NEW 必发，否则回滚日老系统会永久维持抑制）+ 同日应急重发通道；03:30 PHT 前发完。字段契约见[老系统改造需求 §2](./老系统_按日Owner路由改造需求.md#2-接口每日-owner-抑制清单) | ✅ |
| 8 | 测试 topic 演练 | 全流程先在测试 topic 验证（含只发 NEW、空批次、迟到重投），验收通过后切生产 | ✅ |
| 9 | 对比数据集 | 新旧两侧触达 / 回款 / 成本事实按**归属日 + 初始 DPD + 产品**分组产出 | ❌ 不闸灰度，闸效果比较 |

## 2. 明确不需要做的

| 项 | 说明 |
| --- | --- |
| 批次完成信号 | Phase 1 明确不做（契约 §5 已更新）；出现漏发事故后再评估补做 |
| `repaymentEvent` 过滤 | 不做，保持全量（清单 #6） |
| 老系统既有消息格式改造 | 清单走新增独立 topic（#7），不动老系统既有出参与链路 |

## 3. 验收标准

契约 [§6 上线验收表](./数仓_PubSub交付契约.md#6-上线验收)全部通过，另加本机制专属四条：

| # | 验收项 | 通过标准 |
| --- | --- | --- |
| A1 | owner 发布范围 | 生产样本核对：当日发布集合 = 当日 `owner=NEW` 集合；LEGACY 案件零消息 |
| A2 | 归属日 | 抽样 `caseEvent.occurredAt` 的 PHT 日历日 = 目标归属日 |
| A3 | 清单完整性 | 03:30 前到达；零 NEW 日有 `batchEmpty` marker；重放不产生重复（`eventId` 幂等） |
| A4 | userId 分桶 | 同 `userId` 多案同日同 owner；连续日轮换下用户粒度翻转符合比例配置 |

## 4. 演练方式

1. 测试 topic 并行：不动生产 Publisher，测试 topic 上演练全流程（正常日 / 空批次日 / 迟到重投 / `batchSeq` 应急重发）。
2. 新系统侧以影子订阅对账验证（不触达）。
3. 验收通过后生产切换；切换日保留回滚预案（恢复全量发布 + 老系统清单同步回退）。
